## 1. ユースケーステスト（Use Case Testing）

実際のユーザーシナリオをテストケースに変換する技法。クリティカル導線の正常系・代替系を網羅する。

### 適用条件

- クリティカルユーザー導線（ログイン、登録、購入等）
- 複数画面を跨ぐフロー
- 業務上の主要シナリオ

### シナリオ記述フォーマット

```
シナリオ: [シナリオ名]
  前提条件: [ユーザー状態・データ状態]

  1. [操作1]
  2. [操作2]
  ...
  N. [期待される最終結果]
```

### 設計のポイント

- **主導線（Main Flow）**: ユーザーが最も頻繁に辿る正常パス
- **代替導線（Alternative Flow）**: 正常だが異なるパス（例: SNSログイン）
- **例外導線（Exception Flow）**: エラー発生時のパス（例: 認証失敗）
- 主導線1件 + 主要代替導線1件を最小成果物とする

### 例: ユーザー登録フロー

```
シナリオ: 新規ユーザー登録（主導線）
  前提条件: ユーザーは未登録の状態

  1. 登録画面にアクセスする
  2. メールアドレスを入力する
  3. パスワードを入力する
  4. 「登録」ボタンをクリックする
  5. 確認メールが送信される
  6. メール内のリンクをクリックする
  7. 登録完了画面が表示される
```

## 2. 状態遷移テスト（State Transition Testing）

画面やエンティティの状態遷移を網羅的にテストする技法。状態が3以上ある機能に適用する。

### 適用条件

- 状態が3つ以上ある機能（例: 未入力→入力中→下書き→公開 = 4状態）
- 画面のライフサイクル全体で判定する
- 遷移条件が明確に定義できるもの

### 状態遷移図の記述

```
状態遷移図:

   ┌────────┐  [イベント]  ┌────────┐
   │ 状態A  │────────────→│ 状態B  │
   └────────┘              └────────┘
```

### テストケース一覧の記述

| # | 開始状態 | イベント | 終了状態 | 種別 |
|---|----------|----------|----------|------|
| 1 | 状態A | イベント1 | 状態B | 正常遷移 |
| 2 | 状態B | イベント2 | 状態C | 正常遷移 |
| 3 | 状態A | イベント2 | - | 無効遷移 |

### 設計のポイント

- **正常遷移**: 許可された状態変化（最低1件必須）
- **無効遷移**: 許可されていない状態変化の検証（最低1件必須）
- 状態遷移図と一覧表の両方を仕様書に含める
- 全状態ペアの網羅は不要。クリティカルパスと代表的な無効遷移を優先

### 例: 注文ステータス遷移

```
状態遷移図:

   ┌──────────┐  注文確定  ┌──────────┐
   │  カート   │──────────→│  注文済み │
   └──────────┘            └──────────┘
                                │
                    支払い完了   │  キャンセル
                    ↓           ↓
               ┌──────────┐  ┌──────────┐
               │  支払済み │  │キャンセル │
               └──────────┘  └──────────┘
                    │
             発送完了│
                    ↓
               ┌──────────┐
               │  発送済み │
               └──────────┘
                    │
             配達完了│
                    ↓
               ┌──────────┐
               │  完了    │
               └──────────┘
```

| # | 開始状態 | イベント | 終了状態 | 種別 |
|---|----------|----------|----------|------|
| 1 | カート | 注文確定 | 注文済み | 正常遷移 |
| 2 | 注文済み | 支払い完了 | 支払済み | 正常遷移 |
| 3 | 注文済み | キャンセル | キャンセル | 正常遷移 |
| 4 | 支払済み | 発送完了 | 発送済み | 正常遷移 |
| 5 | 発送済み | 配達完了 | 完了 | 正常遷移 |
| 6 | カート | 支払い完了 | - | 無効遷移 |
| 7 | 完了 | キャンセル | - | 無効遷移 |

## 3. デシジョンテーブル（Decision Table）

複数条件の組み合わせをテストする技法。E2E仕様書では最小ケースのみ記載し、詳細はFeature/Unitへ委譲する。

### 適用条件

- 複数の条件が組み合わさる機能
- 条件の組み合わせにより異なる結果が発生する

### 要約フォーマット

| 条件 | ケース1 | ケース2 | ケース3 |
|------|---------|---------|---------|
| 条件A | Y | Y | N |
| 条件B | Y | N | - |
| **結果** | 結果1 | 結果2 | 結果3 |

### 設計のポイント

- E2E対象は**代表的な組み合わせのみ**（全組み合わせはFeature/Unit）
- 条件組み合わせ要約として仕様書に含める
- 網羅的なテストが必要な場合はFeature/Unitテストへ明示的に委譲

## 4. 因子・水準分析（ラルフチャート / HAYST法）

機能の出力を左右する**因子（入力の種類）と水準（取りうる値の区分）**を体系的に洗い出す技法。テストケースの抜け（考慮漏れ）を防ぐ。

### 適用条件

- 入力の種類が多い／状態や環境によって振る舞いが変わる機能
- 「どの入力を組み合わせるべきか」が曖昧な場合

### 目的機能（ユーザーストーリ）を起点にする

因子・水準は「**何のための機能か（目的機能）**」に紐づけて洗い出す。目的機能はユーザーストーリ形式で書く:

> **＜利用者の役割＞**として、**＜ゴール＞**を達成したい。**＜理由＞**のため。

例: 「**入場者**として、**購入済みチケットで入場**したい。**待たずにスムーズに入場する**ため。」

この目的機能に対して inputs/noise/state を洗い出すことで、「何のためのテストか」と因子・水準が一貫し、考慮漏れ（特定の品質特性の不足）を点検しやすくなる。

### 因子の3分類（ラルフチャート）

| 因子の種類 | 意味 | 例 |
|-----------|------|-----|
| **inputs（信号因子）** | 利用者が意図的に与える入力 | フォーム入力値、選択肢、操作順序 |
| **noise（誤差因子）** | 制御できない外乱 | 通信遅延・失敗、同時アクセス、不正データ |
| **state（状態因子）** | 対象が持つ状態 | ログイン状態、在庫数、権限、画面遷移の履歴 |

### 洗い出しフォーマット

| 因子 | 種類 | 水準 | 主に確認する品質特性（ISO/IEC 25010） |
|------|------|------|----------------------------------------|
| メールアドレス | inputs | 有効 / 形式不正 / 空 / 最大長超過 | 機能適合性 |
| 通信状態 | noise | 正常 / タイムアウト / 切断 | 信頼性 |
| 認証状態 | state | 未ログイン / ログイン済 / 期限切れ | セキュリティ |

### 設計のポイント

- **どの品質特性を確認するためのテストか**を因子に紐づけ、特性の抜けを点検する
- E2E では noise/state の代表組み合わせに絞る（全組み合わせは下位レベル）
- 洗い出した因子・水準は、状態遷移テスト・デシジョンテーブル・シナリオ導出の入力になる

## 5. 原因結果グラフ（CEG）→ デシジョンテーブル

仕様の**論理関係（原因＝入力条件、結果＝出力、AND/OR/NOT・制約）**をグラフでモデル化し、そこからデシジョンテーブルを導出する技法。文章では読み取りづらい論理関係や曖昧さを検出できる。

### 適用条件

- 複数条件の論理的な組み合わせで出力が決まる仕様
- 制約（排他・包含・要求）がある仕様
- 仕様の曖昧さ・矛盾・抜けを洗い出したい場合

### 流れ

1. 仕様から**原因（入力条件）・結果（出力）・制約**を抽出する
2. 原因結果グラフでモデル化し、曖昧さ・矛盾・抜けを検出する
3. グラフから**デシジョンテーブル**を導出し、各ルールをテストケースに対応づける
4. E2E対象は代表ルールのみ（網羅は Feature/Unit へ委譲）

### 位置づけ

- 主に **Small / Medium**（仕様ロジックの確認）向け。E2E(Large) には論理網羅を積まない。
- デシジョンテーブル（[3章](#3-デシジョンテーブルdecision-table)）は CEG から導出すると抜け漏れが減る。
- 技法の詳細・支援ツール（CEGTest）は `test-methodology-reviewer` の `references/technique-selection.md` を参照。

> **AI生成時の注意**: AIに原因結果グラフ／デシジョンテーブルを生成させる場合、各ルールの期待結果が**仕様に根拠づくか**を必ずレビューする（一般知識による期待結果の捏造に注意）。
