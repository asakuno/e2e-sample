## Overview

画面仕様書からE2Eテスト仕様書を7ステップで生成するワークフロー。

**出力先**: `tests/e2e/specs/{category}/{screen}.spec.md`

---

## ワークフロー

### [1/7] 入力成果物の解析

E2Eテスト設計は画面仕様書だけでは不十分。**画面遷移図・アクティビティ図を含む設計成果物**を入力にする。詳細は `references/input-artifacts-and-risk.md` を参照。

1. 引数 `$1` から画面仕様書パスを取得（空の場合はユーザーに質問）
2. Readツールで画面仕様書を読み込み、以下を特定:
   - **画面情報**: 画面ID、画面名、URL、認証要否
   - **画面要素**: フォーム要素、表示要素、ナビゲーション要素
   - **機能一覧**: 主要機能、副次機能
   - **バリデーションルール**: 全層割当の対象
3. **設計成果物の確認**（E2E設計の根拠に必須）:
   - **画面遷移図**: 状態遷移テスト・画面横断シナリオの根拠。**無い場合は強く推奨**としてユーザーに作成/提供を促す
   - **アクティビティ図**: シナリオ導出・分岐網羅の根拠
   - **コンポーネント図/コミュニケーション図**（あれば）: Test size 決定（依存境界）の根拠
   - **業務一覧/リスク情報**（あれば）: リスクベース選定の入力
   - 画面遷移図/アクティビティ図が提供されない場合は、画面仕様書からの**推測で補い、その旨と限界を仕様書の前提条件に明記**する
4. 複数画面が含まれる場合、対象画面をユーザーに確認

### [2/7] 既存テスト分析

重複テスト作成を防止するため、既存テストを調査する。

1. `tests/e2e/specs/**/*.spec.md` と `tests/e2e/tests/**/*.spec.ts` をGlobで検索
2. 以下をチェック:
   - **完全重複**: 同一画面・同一機能のテスト仕様書が既に存在しないか
   - **部分重複**: 類似テストケース（同じ操作手順）が既に存在しないか
   - **関連テスト**: 依存関係のあるテスト（ログイン→ダッシュボード等）が存在するか
3. 分析結果をユーザーに報告し、続行/確認/キャンセルを選択

### [3/7] リスク分析・責務分類・技法選定

E2E過多を防ぎ、優先度の根拠を明確にするため、テストケース設計前に「**リスク → 責務/サイズ → 技法**」の順で整理する。詳細は `references/input-artifacts-and-risk.md`、技法は `references/technique-patterns.md` を参照。

#### 3-1. リスクベース選定（機能不動作起点）

**分析単位**: テストベースから業務を抽出し、共通項を**機能的責務**単位にまとめてリスク分析する（保守しやすい。チーム構成/アーキテクチャに応じて単位を調整）。

1. 機能不動作リスクを抽出（「この機能（機能的責務）が動かないと、誰がどう困るか」）
2. ステークホルダ別の影響を評価（利用者／運用者／経営／その他）
3. 重篤度（S/A/B）× 発生頻度（High/Medium/Low）で優先度を付ける
4. **生成する仕様書のリスク表に記録**する（リスク表のフォーマットは `references/input-artifacts-and-risk.md` を参照。reference ファイル自体は編集しない）。業務一覧/リスク情報が無ければ担当者と簡易見積もりし、根拠を明記

#### 3-2. 責務分類（レベル）とTest size（依存境界）

1. 要件をレベルに分類:
   - **E2E**: クリティカル導線、複数画面を跨ぐフロー、認証/認可の主要遷移、重大リスク
   - **Feature**: リクエストバリデーション、DB永続化、認可詳細
   - **Unit**: 細かい分岐、計算、データ変換
2. E2E対象判定: 画面横断 or 業務クリティカル or 高リスク（3-1の優先度）。入力バリデーション詳細・論理分岐は Feature/Unit を優先
3. **Test size を併用**: E2Eに残すのは Large 相当の「代表シナリオ/Happy path/重大リスク」に限定。ロジック分岐は Small/Medium へ。**サイズ判断はコンポーネント図/コミュニケーション図の依存境界を根拠**にする（`Skill('test-methodology-reviewer')` の `references/coverage-strategies.md` を参照）

#### 3-3. 技法選定ゲート

該当する項目のみ判定し、結果と根拠を記録する（該当なしの場合も「該当なし」と明記）。全Noの場合はユースケーステストをデフォルト適用。

- **クリティカルユーザー導線か**: Yes → ユースケーステスト。シナリオは**画面遷移図×アクティビティ図から導出**（`Skill('playwright-guidelines')` の `references/scenario-derivation.md`）
- **状態が3以上あるか**: Yes → 状態遷移テスト（**画面遷移図を根拠**にする。例 未入力→入力中→下書き→公開 = 4状態）
- **入力の種類が多い／状態・環境で振る舞いが変わるか**: Yes → 因子・水準分析。**目的機能（ユーザーストーリ形式）を起点**に inputs/noise/state を洗い出して考慮漏れを点検
- **複数条件の論理的な組み合わせがあるか**: Yes → 原因結果グラフ→デシジョンテーブル要約（E2E対象は代表ルールのみ。詳細は `Skill('test-methodology-reviewer')` の `references/technique-selection.md`）

#### 3-4. 責務マトリクス作成

`references/responsibility-matrix-format.md` の形式で作成:
- Feature/Unitは **ID・委譲先パス・理由(1行)** のみ記載
- Feature/Unitの詳細手順・期待結果はE2E仕様書に記載しない

リスク表・責務マトリクス・技法選定結果をユーザーに提示し、承認後に次へ進む。

### [4/7] テストケース設計

> **Seed整合チェック（条件付き）**: 初めて仕様書を作成する画面カテゴリ、または既存仕様書と構成（見出し・テーブル列・ID命名）が不統一な場合、`references/seed-spec-examples.md` の構成と整合確認し調整する。Seedのログイン仕様書例は `Skill('playwright-guidelines')` の `references/examples/login-example.md` の実装例と対応する。

1. `Skill('playwright-guidelines')` を参照（テスト仕様書フォーマット、Page Objectパターン、セレクタ戦略）
2. **責務マトリクスでE2Eに分類された要件のみ**テストケースを設計:

| 分類 | 内容 |
|------|------|
| **正常系** | 基本フロー、代替フロー、オプショナルフロー |
| **異常系** | 認証エラー、高リスクな失敗フロー、サーバーエラー |
| **境界値** | E2E対象に分類された入力のみ |

3. **バリデーション要件の全層割当100%（必須）**:
   - 仕様書のバリデーションルールをE2E/Feature/Unitのいずれかに必ず割り当てる
   - E2Eで100%実装する必要はない
   - 詳細は `references/validation-coverage-format.md` を参照
4. 技法ごとの最小成果物を作成:
   - **ユースケーステスト適用時**: 画面遷移図×アクティビティ図から導出した主導線1件 + 主要代替導線1件
   - **状態遷移テスト適用時**: 状態遷移一覧（正常遷移1件以上 + 無効遷移1件以上。**画面遷移図を根拠**にする）
   - **因子・水準分析適用時**: 因子・水準表（inputs/noise/state と確認する品質特性）。E2Eは代表組み合わせのみ
   - **原因結果グラフ/デシジョンテーブル適用時**: 条件組み合わせ要約（CEGから導出。E2E対象は代表ルールのみ）
5. 優先度を設定（高: クリティカルパス、中: エラーハンドリング、低: エッジケース）
6. テストケース構成をユーザーに確認（承認/高優先度のみ/却下）

### [5/7] テスト仕様書生成

`Skill('playwright-guidelines')` のテスト仕様書フォーマットに従って作成:

- 画面概要（画面ID、画面名、URL、認証）
- 前提条件（**入力成果物：画面遷移図/アクティビティ図の有無と、無い場合の推測の限界も明記**）
- **リスク表（必須）**: リスクベース選定の結果（失敗シナリオ例・影響・重篤度×発生頻度・優先度・**根拠（テストベース/機能ID）**・割当）
- 技法選定結果（判定・採用技法・根拠）
- テストケーステーブル（テストID、テスト名、前提条件、操作手順、期待結果、優先度）
- データ要件（テストデータ、Laravelファクトリー）
- Page Object要件
- **責務マトリクス（必須）**
- **状態遷移一覧（該当時必須）**
- **因子・水準表（該当時必須）**
- **条件組み合わせ要約（CEGから導出。該当時必須）**
- **トレーサビリティマトリクス（必須）**

**テストID命名規則**: `{CATEGORY}_{SCREEN}_{連番}` または `{CATEGORY}_{SCREEN}_{種別}_{連番}`

#### 責務マトリクス

要件ごとにE2E/Feature/Unitの責務を明確化する。フォーマットは `references/responsibility-matrix-format.md` を参照。
E2E仕様書では、Feature/Unitは委譲情報のみを記載し、詳細ケースは対応するFeature/Unitテストへ分離する。

#### トレーサビリティマトリクス

全画面要素とテストケースの紐付けを記録する。機能種別ごとの必須カバレッジ:

| 機能種別 | 必須テスト |
|---------|----------|
| **入力** | E2E対象のみ 正常系✓ 異常系✓ 境界値✓ |
| **表示** | 正常系✓、条件分岐がある場合は異常系✓ |
| **ナビゲーション** | 遷移先確認テスト✓ |

未テスト要素は [6/7] 品質チェックで報告する。

### [6/7] 品質チェック

以下の17項目を検証する:

| # | 項目 | 確認内容 |
|---|------|---------|
| 1 | クリティカル導線正常系カバレッジ | 主要ジャーニーすべてに正常系E2Eテスト存在 |
| 2 | 高リスク異常系カバレッジ | 認証エラー、重要失敗フローの異常系テスト存在 |
| 3 | **クリティカル導線E2E 100%** ★ゲートA | E2E対象クリティカル導線がすべてE2Eケースに反映 |
| 4 | **バリデーション全層割当100%** ★ゲートB | 全バリデーションルールがE2E/Feature/Unitいずれかに割当済 |
| 5 | 責務分類の妥当性 | E2E過多でなく、詳細がFeature/Unitへ適切に委譲 |
| 6 | 技法選定根拠の明確性 | 採否が根拠付きで記載 |
| 7 | 状態遷移一覧の整備 | 状態3以上で正常/無効遷移各1件以上 |
| 8 | 条件組み合わせ要約の整備 | 複数条件でE2E対象の最小ケース |
| 9 | 非E2E詳細混入なし | Feature/Unitの詳細手順がE2E仕様書に混入していない |
| 10 | 前提条件の具体性 | 認証状態・データ状態が明確 |
| 11 | 操作手順の再現性 | 第三者が再現可能な粒度 |
| 12 | 期待結果の検証可能性 | 具体的に検証可能な記述 |
| 13 | トレーサビリティ完全性 | E2E対象要素がテストケースに紐付け |
| 14 | 入力成果物の活用 | 状態遷移・画面横断シナリオが画面遷移図/アクティビティ図に基づき、Test size判断がコンポーネント図/コミュニケーション図の依存境界に基づく（無い場合は推測の限界を明記） |
| 15 | リスク優先度の根拠 | 重篤度×発生頻度・ステークホルダ影響・**失敗シナリオ例・根拠（テストベース/機能ID）**がリスク表に記録 |
| 16 | 期待結果の仕様根拠 | 各期待結果がテストベース（仕様）に根拠づく（AIの一般知識による捏造でない） |
| 17 | 因子・水準表の整備（該当時） | 因子・水準分析を採用した場合、inputs/noise/state の因子・水準表が存在 |

**★ゲートA/B**: いずれか未達の場合、次のステップへ進めない。

**品質スコア**: `(合格項目数 / 17) × 100`

| スコア | 判定 | アクション |
|--------|------|----------|
| 100% | 合格 | 次のステップへ進む |
| 70-99% | 条件付き合格 | 警告を表示し、修正を推奨 |
| 0-69% | 不合格 | 修正必須、再チェックが必要 |

**Seed整合チェック（Warning）**: 仕様書の形式・粒度が `references/seed-spec-examples.md` と整合しているか確認。未達でもゲートに影響しないが修正推奨。

報告フォーマットと修正指示例は `references/quality-checklist.md` を参照。
品質チェック結果をユーザーに報告し、承認/修正/却下を選択。修正選択時は不合格項目を修正後、再チェック。

### [7/7] 完了と次ステップ

サマリーを表示し、次のアクションをユーザーに確認:
- **テストコード生成**: `Skill('implementing-e2e-specs')` でPlaywrightテストを生成
- **レビュー指摘を反映**: テスト仕様書を修正
- **完了**: テスト仕様書作成のみで終了
