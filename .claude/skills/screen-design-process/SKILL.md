# 画面設計プロセスガイド

エンジニアが「白紙の状態」から「画面構成の決定」までを論理的に進めるための思考プロセスとワークフロー。

> **棲み分け**: このスキルは「何を、どう並べるか」（設計初期）をカバーする。
> 「どう見せるか、基準を満たすか」（設計後期）は `ui-design-guidelines` を参照。

## マインドセット転換: SE思考 vs デザイナー思考

画面設計がうまくいかない根本原因は「センスがない」ことではなく、**思考の手順が異なる**こと。

### SE の典型的アプローチ（"+α" 思考）

```
情報を表で整理 → 機能を追加 → 説明を追加 → 色を付ける → 装飾する
```

- DB のカラムをそのまま画面に並べる
- 「全ての情報を漏れなく表示する」が目標
- デザインは最後に「見栄えを整える」工程

### デザイナーのアプローチ（"設計そのもの" 思考）

```
利用シーンを想像 → 情報をグループ化・加工 → 強弱を付けて配置 → 機能を追加 → 装飾する
```

- ユーザーが「何を知りたいか」から始める
- 「最も重要な情報が最も目立つ」が目標
- デザインは最初から設計の一部

### 重要な気づき

- デザインは「センス」ではなく**「手順とポイント」**
- SE もデザイナーの手順を踏めば、十分に良い画面を設計できる
- 違いは才能ではなく、**何から始めるか**の順序

## 画面設計 7 ステッププロセス

### Step 1: 利用シーンを想像する

画面を設計する前に、以下を明確にする:

- **誰が** 使うのか（役割、スキルレベル、ドメイン知識）
- **どこで** 使うのか（オフィス、現場、移動中）
- **どんな端末で** 使うのか（デスクトップ、タブレット、スマホ）
- **どんなシーンで** 使うのか（じっくり分析、素早く確認、緊急対応）
- **何を達成したいのか**（意思決定、データ入力、状況把握）

```
例1: 「営業マネージャーが、外出先のタブレットで、
      今週の売上状況を素早く把握したい」

→ 大きな数字で要約表示、詳細はドリルダウン、
  タッチ操作前提のUI

例2: 「ジムのトレイナーが、トレーニングルームのタブレットで、
      会員の個人情報確認・前回の状況確認・次回予約受付をしたい」

→ 会員の顔写真と名前を大きく表示（1秒で誰か分かる）、
  前回のトレーニング内容と伝達事項を一覧で確認、
  片手タップで次回予約を入れられるUI
```

**チェック**: 利用シーンを1文で説明できるか？ できなければ、画面の目的が曖昧。

### Step 2: 使える情報を洗い出す

**まず表にまとめない。** 情報をフラットに並べて「じっと眺める」ことから始める。
DB カラムの一覧ではなく、**ユーザー視点**で使える情報を列挙する。

```
NG: いきなり表（テーブル）を作って情報を整理しようとする
OK: 情報をフラットに書き出して、何が本当に必要かを眺める
```

| NG（DB視点）           | OK（ユーザー視点）                   |
| ---------------------- | ------------------------------------ |
| `user_id`              | 担当者名                             |
| `created_at`           | 登録日（いつ登録されたか）           |
| `birth_date`           | 年齢（何歳か）                       |
| `status_code`          | 現在の状態（進行中/完了/保留）       |
| `price`, `tax_rate`    | 税込価格                             |

**ポイント**: 「このデータがあると、ユーザーは何が判断できるか？」を問う。

### Step 3: 不要な要素を削る

追加する前に、**削れるものを探す**。

**まずラベルを全部消してみる。** そして「伝わらないものだけ最小限のヒントを補完する」:

```
ラベル全削除後:
  123              → 何の番号か不明 → 「会員No. 123」を補完
  砂金 太郎        → 名前だと分かる → そのまま
  1984.10.16       → 日付だが何の日付か不明 → 「1984.10.16 生まれ」を補完
  03-1234-5678     → 電話番号だと分かる → そのまま
  user@example.com → メールだと分かる → そのまま
```

以下の問いで検証する:

- **ラベルを消しても伝わるか？** → フォーマットで自明ならラベル不要。不明なものだけ最小限の補完を加える
- **線なしでも区別できるか？** → 余白だけでグループを表現できないか
- **この情報がなくてもユーザーは目的を達成できるか？** → 「更新日時」は本当に必要か
- **デフォルト値は表示する必要があるか？** → 「通知設定: ON」がデフォルトなら、OFFの時だけ表示
- **同じ情報を別の形で既に表示していないか？** → グラフと表で同じデータを重複表示

```
削除の判断基準:
- 80%のユーザーが80%の場面で必要としない → 削る or 折りたたむ
- あると便利だが、なくても致命的ではない → 折りたたむ or 別画面
- 表示しないとエラーや誤操作が起きる → 残す
```

### Step 4: 情報をグルーピング・優先順位付けする

残った情報を**用途別にグループ化**し、**優先順位**を付ける。

**グルーピングの軸**:
- タスク別: 「確認する情報」「操作する情報」「参考情報」
- 時間軸別: 「今」「過去」「未来」
- 重要度別: 「常に表示」「条件付き表示」「詳細で表示」

**優先順位の付け方**:

| 優先度 | 基準                             | 画面上の扱い                 |
| ------ | -------------------------------- | ---------------------------- |
| P1     | これがないと画面の目的を果たせない | 最も目立つ位置に大きく表示   |
| P2     | あると判断が速くなる             | P1の近くにやや控えめに表示   |
| P3     | 一部のユーザーが時々必要とする   | 折りたたみ or 別セクション   |

```
例: 注文一覧画面
  P1: 注文番号、顧客名、金額、ステータス
  P2: 注文日、配送先、支払方法
  P3: 内部メモ、更新履歴、担当者変更ログ
```

### Step 5: データを加工する

生データをそのまま表示せず、**ユーザーが理解しやすい形に変換**する。

| 生データ                  | 加工後                        | 理由                       |
| ------------------------- | ----------------------------- | -------------------------- |
| `1990-05-15`              | 34歳                          | 年齢が知りたい、日付ではない |
| `2024-03-17T14:23:00Z`   | 2日前                         | 相対時間の方が直感的       |
| `4.7` (評価)              | ★★★★★ (4.7)                  | 視覚的に品質が伝わる       |
| `090-1234-5678`           | 📞 090-1234-5678              | アイコンで種別が一目瞭然   |
| `3`（件数）               | 未読 3件（バッジ表示）        | 文脈を付けて意味を明確に   |
| `85` (%)                  | プログレスバー 85%            | 進捗は棒グラフが直感的     |
| `150000` (円)             | ¥150,000                      | 桁区切りで読みやすく       |
| `PENDING_REVIEW`          | レビュー待ち（黄色バッジ）    | コードではなく日本語+色    |
| `true` / `false`          | ✓ / −                         | 一覧ではアイコンが効率的   |
| `John Smith`（担当者）    | JS（アバター）+ John Smith    | アバターで視認性向上       |

**加工の判断基準**: 「このデータを見て、ユーザーは0.5秒以内に意味を理解できるか？」

### Step 6: レイアウトを選定し強弱をつけて配置する

情報の構造と優先順位に基づいて、最適なレイアウトを選ぶ。

**レイアウト選定クイックリファレンス**:

| レイアウト | 最適な場面                           | 避けるべき場面                   |
| ---------- | ------------------------------------ | -------------------------------- |
| テーブル   | 比較・ソート・一括操作が必要         | 項目が少ない、画像中心           |
| カード     | ビジュアル重要、項目数が少ない       | 比較が必要、大量データ           |
| リスト     | 時系列、シンプルなデータ             | 画像が主役、複雑な比較           |
| グリッド   | 画像/ビジュアルが主役               | テキスト中心、比較が必要         |
| マスター/詳細 | 一覧と詳細を同時に見たい          | モバイル、シンプルなデータ       |

> 詳細なレイアウト判断フローは `references/layout-decision-framework.md` を参照。

**強弱のつけ方**:
- **サイズ**: 重要な情報ほど大きく（P1 > P2 > P3）
- **位置**: 重要な情報ほど上・左に（F型/Z型の視線パターン）
- **コントラスト**: 重要な情報ほど濃く、補足情報は薄く
- **余白**: 重要なグループの周囲に十分な余白を確保

### Step 7: 機能を追加し装飾で「どういうものか」を表現する

最後に、インタラクションと装飾を追加する。

**装飾の役割は「説明」**:
- **押せるもの** → ホバー効果、カーソル変化、微妙な影
- **重要なもの** → 色、太字、バッジ、アイコン
- **危険なもの** → 赤色、警告アイコン、確認ダイアログ
- **隠れた機能** → ツールチップ、右クリックメニュー
- **状態があるもの** → トグルの見た目、選択状態の視覚的変化
- **グループの境界** → カードの枠、セクションの背景色、区切り線

```
装飾で答えるべき問い:
- 「これは押せるのか？」
- 「これは重要なのか？」
- 「これはどういう状態なのか？」
- 「この操作は取り消せるのか？」
```

## 出力フォーマット

7ステップの成果を以下の形式でまとめ、ユーザーに提示する:

### 1. 利用シーン要約
```
「[誰が]、[どこで/どんな端末で]、[何を達成したいか]」（1文）
```

### 2. 情報一覧（優先順位付き）
```
P1（常に表示）: 項目A、項目B、項目C
P2（補足表示）: 項目D、項目E
P3（折りたたみ/別画面）: 項目F、項目G
削除: 項目H（理由: ...）
```

### 3. データ加工方針
```
項目A: 生データ → 加工後の形（理由）
項目B: 生データ → 加工後の形（理由）
```

### 4. レイアウト方針
```
レイアウト: [テーブル/カード/リスト/グリッド/マスター詳細/ハイブリッド]
選定理由: ...
レスポンシブ: デスクトップ→タブレット→モバイルでの変換方針
```

### 5. 画面スケッチ（ASCII ワイヤーフレーム）
```
┌─────────────────────────────┐
│  実際のレイアウトをASCIIで   │
│  表現する                    │
└─────────────────────────────┘
```

### 6. ui-design-guidelines への引き渡し事項（該当する場合）
```
- タイポグラフィ: P1/P2/P3のサイズ・ウェイト方針
- カラー: ステータス色、アクセントカラーの用途
- インタラクション: 主要操作のフィードバック方針
```

## SE の心得 6 か条

### 1. いきなり表を作るところから始めない

テーブルは万能ではない。まず Step 1-4 を踏んでから、テーブルが本当に最適かを判断する。

### 2. なくても伝わるものは削る

ラベル、罫線、枠線、「該当なし」表示 ── 余白やフォーマットで代替できないか常に問う。引き算のデザインが洗練を生む。

### 3. 情報は強弱をつける

全ての情報を同じサイズ・同じ色で並べない。P1/P2/P3 の優先順位を視覚的に表現する。

### 4. データの加工を厭わない

`birth_date` をそのまま表示するのは怠慢。ユーザーが必要としているのは「年齢」であり「日付」ではない。

### 5. 装飾で「どういうものか」を表現する

装飾は「見た目を良くする」ためではなく、「これが何であり、どう操作するか」を伝えるためにある。

### 6. 設計とデザインを線引きして区別しない

「設計はSEの仕事、デザインはデザイナーの仕事」という線引きをやめる。画面の情報構造を決めることは、既にデザインの一部。

## `ui-design-guidelines` との連携

本スキルの成果物を `ui-design-guidelines` に引き渡すポイント:

| 本スキルの成果物         | 引き渡し先                                      |
| ------------------------ | ----------------------------------------------- |
| 情報の優先順位マップ     | → タイポグラフィ階層（サイズ・ウェイト決定）    |
| レイアウト方針           | → 4pxグリッド配置、レスポンシブブレークポイント |
| データ加工方針           | → カラー設計（ステータス色等）                  |
| インタラクション方針     | → アニメーション・モーション設計                |
| 画面全体の構成           | → アクセシビリティ検証チェックリスト            |

**ハンドオフのタイミング**:
1. 本スキルで情報構造とレイアウトが確定
2. `ui-design-guidelines` でビジュアル精度を上げる
3. `ui-design-guidelines` の Phase 4 で検証

## アンチパターン集

エンジニアがよくやるNG例と改善方向。Before/After のワイヤーフレームは `references/antipattern-visuals.md` を参照。

### 1. DB直結テーブル
```
❌ SELECT * の結果をそのままテーブルに表示
✅ ユーザーが必要な情報だけを選別し、加工して表示
```

### 2. 全情報フラット表示
```
❌ 20項目を全て同じサイズで1画面に表示
✅ P1を大きく、P2を標準、P3を折りたたみに
```

### 3. ラベル過剰
```
❌ 名前: 田中太郎  メール: tanaka@example.com  電話: 090-xxxx-xxxx
✅ 田中太郎
   tanaka@example.com
   📞 090-xxxx-xxxx
   （フォーマットとアイコンで種別が分かる）
```

### 4. 生データそのまま
```
❌ created_at: 2024-03-17T14:23:00.000Z
✅ 2日前
```

### 5. 罫線・枠線過剰
```
❌ 全てのセル、全てのセクションに枠線
✅ 余白とグルーピングで視覚的に分離
```

### 6. 均等配置
```
❌ 全てのボタン、全てのカードを同じサイズで均等配置
✅ 主要アクションを大きく、副次アクションを小さく
```

### 7. 機能優先の画面構成
```
❌ 「この画面でできること」を軸に構成（CRUD操作別タブ）
✅ 「ユーザーが達成したいこと」を軸に構成（タスクフロー）
```

### 8. 説明テキスト過剰
```
❌ 「このボタンを押すと、選択したアイテムが削除されます」
✅ 🗑 削除（赤色、確認ダイアログ付き）
   （装飾で「危険な操作」であることを表現）
```
