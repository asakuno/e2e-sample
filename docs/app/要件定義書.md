# 株式投資情報分析Laravelアプリ 要件定義書

## 1. 概要

本システムは、ユーザーが登録した監視銘柄に対して、株価、ニュース、開示情報、マクロ経済情報などを収集し、株価の上下に影響しうる材料を整理・分析する株式投資情報分析アプリケーションである。

本システムは、保有株管理、損益管理、自動売買、証券口座連携を目的としない。あくまで、売買判断に必要な情報を収集・要約・分類・スコアリングし、ユーザーが投資判断を行うための材料を整理することを目的とする。

## 2. システムの目的

### 2.1 主目的

ユーザーが監視している銘柄について、株価に影響しうる情報を効率的に把握できるようにする。

### 2.2 具体的な目的

- 監視銘柄の株価情報を確認できるようにする
- 銘柄に関連するニュースを収集・保存する
- ニュースや開示情報をAIで要約・分類する
- 株価に対してポジティブ、ネガティブ、中立のどの材料かを可視化する
- 影響度スコアを算出し、銘柄ごとのシグナルとして表示する
- ユーザーが売買判断の材料を素早く確認できるようにする

## 3. 対象ユーザー

### 3.1 想定ユーザー

- 個人投資家
- 米国株を中心に取引しているユーザー
- 日本株も一部監視したいユーザー

- AIによる要約、分類、材料整理を活用したいユーザー

### 3.2 初期MVPでの想定

初期MVPでは、個人利用または少人数利用を前提とする。多人数向けSaaS、課金機能、プラン制御、組織管理などは対象外とする。

### 概要

- 概要
- 本文
- URL
- 配信元
- 公開日時
- 関連銘柄
- データ取得元

### MVPでの方針

無料API中心とするため、ニュース本文全文の取得は必須としない。取得可能なタイトル、概要、URL、公開日時、配信元を保存し、それらをもとにAI分析を行う。

### テーブル案

```text

- id
- title
- summary
- body
- url
- source
- published_at
- hash
- created_at
- updated_at
```

```text

- id
- stock_id
- news_article_id
- created_at
- updated_at
```

### 重複排除

同一記事の重複保存を避けるため、URLまたはハッシュ値を用いる。

```text

```

## 6.7 AI分析基盤

### 基本方針

AI分析機能は、特定のAIサービスに密結合しない。`ArticleAnalyzerInterface` を定義し、外部LLM APIおよび自前ホストLLMの双方に差し替え可能な構成とする。

### MVP方針

MVPでは、OpenAI API等の外部LLM APIを利用する。

### 将来方針

将来的には、Gemma、Llama、Qwen等のオープンウェイトモデルをGPUサーバー上にホストし、`LocalLlmArticleAnalyzer` 経由で分析処理に利用できる構成とする。

### 使用しないもの

Codex Appはアプリケーション実行時のAI分析エンジンとしては使用しない。

Codex Appは以下の用途に限定する。

- Laravel実装支援
- migration作成
- Model作成
- Service作成
- Job作成
- Command作成
- テスト作成
- リファクタリング
- コードレビュー

### インターフェース案

```php
interface ArticleAnalyzerInterface
{
    public function analyze(NewsArticle $article, Stock $stock): ArticleAnalysisResult;
}
```

### 実装クラス案

```php
class OpenAiArticleAnalyzer implements ArticleAnalyzerInterface
{
    // OpenAI API等の外部LLM APIを利用する
}
```

```php
class LocalLlmArticleAnalyzer implements ArticleAnalyzerInterface
{
    // 自前ホストLLM APIを利用する
}
```

### 環境変数案

```env
AI_ANALYZER_PROVIDER=openai
# AI_ANALYZER_PROVIDER=local
LOCAL_LLM_ENDPOINT=https://llm.example.com/analyze
```

## 6.8 シグナルスコア機能

### 概要

銘柄ごとに、直近のニュース分析結果を集計し、シグナルスコアとして表示する。

### スコア範囲

```text
-10 〜 +10
```

### スコアの意味

```text
+7 〜 +10: 強いポジティブ材料
+3 〜 +6: ややポジティブ
-2 〜 +2: 中立
-3 〜 -6: ややネガティブ
-7 〜 -10: 強いネガティブ材料
```

### MVPでの算出方針

MVPでは、直近ニュースの `impact_score` をもとに集計する。

例:

```text
total_score = 直近24時間または直近7日間のimpact_score平均
```

### 将来的な算出方針

将来的には以下を組み合わせる。

- ニューススコア
- 開示情報スコア
- マクロ経済スコア
- 株価変動スコア
- 出来高変化スコア

### テーブル案

```text
stock_signals
- id
- stock_id
- signal_date
- short_term_score
- medium_term_score
- news_score
- disclosure_score
- macro_score
- total_score
- reason
- created_at
- updated_at
```

## 13. 非機能要件

## 13.1 セキュリティ

- 認証済みユーザーのみウォッチリストを操作できる
- 他ユーザーのウォッチリストは閲覧・編集できない
- 他ユーザーのアラートは閲覧・編集できない
- 外部APIキーは `.env` で管理する
- APIキーをフロントエンドに露出しない
- 管理系機能には認可制御を行う

## 13.2 パフォーマンス

- 外部API取得処理はQueue Jobで非同期化する
- 画面表示時に外部APIを直接呼ばない
- 取得済みデータをDBに保存して表示する
- 一覧画面はページネーションする
- 銘柄詳細画面ではEager Loadingを利用する

## 13.3 可用性

- 外部APIが失敗しても画面全体を落とさない
- API取得失敗時はログに記録する
- 失敗Jobは再実行可能にする
- AI分析失敗時もニュース自体は表示できるようにする

## 13.4 保守性

- Controllerに分析ロジックを書かない
- 外部API連携はServiceに分離する
- 定期実行はCommandで管理する
- 重い処理はJobに分離する
- AI分析はInterfaceを介して実装する
- モデル名、プロンプトバージョンをDBに保存する

## 13.5 コスト管理

無料API中心で構成するため、API利用量を抑える設計とする。

AI分析については、以下の方針でコストを抑える。

- ウォッチリスト関連ニュースのみ分析する
- 同じURLは再分析しない
- 同一または類似タイトルの記事は重複排除する
- 古いニュースは分析対象外にする
- 重要度の低いニュースはAI分析しない
- prompt_versionを管理し、再分析対象を制御する

## 15. 売買推奨に関する制約

本システムでは以下の表現を避ける。

- この株は買いです
- この株は売りです
- 明日は上がります
- 必ず上昇します
- 売却すべきです
- 購入すべきです

代わりに以下のような表現を使用する。

- ポジティブ材料が多い
- 短期的には買い材料として解釈されやすい
- 過去類似ケースでは上昇傾向が見られる
- ネガティブ材料として警戒されやすい
- 市場全体の地合いには注意が必要
- 投資判断には追加確認が必要
